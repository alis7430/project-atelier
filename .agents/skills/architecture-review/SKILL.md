# Architecture Review

개발자가 구현할 구조를 판단할 수 있도록 현재 책임과 수명을 설명하고,
필요한 변경만 제안한다. 한국어로 답하고 실제 코드 식별자를 유지한다.
개별 메서드의 결함 검토가 주목적이면 code-review, 새 기능 설계가 주목적이면
feature-design의 범위를 참고하되 세 스킬의 전체 절차를 반복하지 않는다.

## 컨텍스트와 실행 범위

- 경로는 프로젝트 루트 기준이다. `AGENTS.md`, `Docs/AI/PROJECT.md`,
  `Docs/AI/CURRENT.md`와 관련 `ARCHITECTURE.md`·`DECISIONS.md`를 확인한다.
  이번 작업에서 이미 읽은 문서는 재사용하고 과거 이유가 필요할 때만 SESSIONS를 읽는다.
- 생산 코드·자산·설정은 읽기 전용이다. Unity 실행, 빌드, 테스트,
  패키지 조작과 자동 수정은 수행하지 않는다. C# 예시는 채팅에만 제공한다.
- 문서 갱신은 먼저 제안한다. 명시적 반영 요청이 있으면 승인된 문서 범위만
  편집할 수 있으며, 이미 받은 승인을 반복해서 묻지 않는다.

## 검토 방법

1. 질문의 시스템 경계를 정하고 관련 클래스·인터페이스, 호출자와 소비자,
   asmdef 및 필요한 씬·프리팹·설정 자산을 읽는다. 좁은 질문에 전체 저장소를 재분석하지 않는다.
2. 생성 주체, 초기화 순서, 데이터 소유자, 변경 주체, 이벤트 구독·해제,
   씬 전환·Clear·반환·파괴 시점을 추적한다. 컴포넌트 존재와 실제 호출 연결을 구분한다.
3. 정적 의존성, 런타임 호출, 데이터 흐름을 구분한다. Managers를 다시 참조한다는
   이유만으로 어셈블리 순환 참조나 무한 재귀라고 단정하지 않는다.
4. 현재 구조를 Accepted 결정과 비교한다. 구현 사실, 승인된 의도,
   미구현 연결, 조건부 위험, 미검증 사항을 분리한다. 문서를 소스 확인의 대체물로 쓰지 않는다.
5. 현재 구조 유지 또는 작은 변경을 우선 검토한다. 선택에 실질적인 차이가 있을 때만
   대안을 비교하고, 변경 파일·직렬화 호환성·수명·개발자 검증 비용을 설명한다.

## Project Atelier에서 중요한 경계

- 현재 목표와 결정은 Docs/AI를 기준으로 매번 확인한다. 기술 스택과 개발 단계의
  상세 스냅샷을 이 스킬에 중복 저장하지 않는다.
- 맵 관련 검토는 `Assets/_Projects/Scripts/Map/`의 모델·생성·진행·표시와
  `Assets/_Projects/Scripts/Map/Test/MapTestScene.cs`의 연결 책임을 추적한다.
- 현재 테스트 연결 책임은 MapTestScene이다. 씬 미연결은 알려진 개발 단계이므로
  회귀로 단정하거나 최종 구성 계층 도입을 화면 확인의 선행조건으로 만들지 않는다.
- 향후 RunManager의 런 데이터 수명과 현재 Managers.Clear의 씬 정리를 구분한다.
  RunManager가 이미 구현되었다거나 RuntimeManager의 단순 이름 변경이라고 가정하지 않는다.
- 풀링된 표시 객체의 수명과 맵·시드·방문 상태의 수명을 분리한다.
  씬 간 상태 보존이 디스크 저장 요구를 뜻하지는 않는다.
- `Packages/urdev-game-framework/Runtime/`의 실제 식별자를 확인한다.
  목표 명칭 URDev.GameFrameWork를 기존 소스 심볼 대신 사용하지 않는다.
- 개인 Memo.md와 외부 레퍼런스는 승인된 결정이 아니다.
  외부 소스를 비교했다면 실제 열어 본 URL·파일과 확인 범위를 밝힌다.

## 결과

- 핵심 판단과 현재 구조를 먼저 설명하고 실제 경로·심볼·확인한 줄을 근거로 제시한다.
- 책임이나 흐름이 복잡할 때만 표 또는 작은 Mermaid 다이어그램을 사용한다.
  구현된 흐름과 예정된 연결은 구분해서 표시한다.
- 권고, 필요한 경우의 대안, 수동 적용 영향과 개발자 검증 항목을 제시한다.
  현재 구조가 적절하면 변경이 필요 없다고 명시한다.
- 문서에 남길 변화가 있으면 해당 문서와 복사 가능한 수정안을 제안한다.
  새 제안은 Proposed, 관찰은 Observed로 구분하고 명시적 승인 없이 Accepted로 올리지 않는다.
